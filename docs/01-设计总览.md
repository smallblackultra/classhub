## 0. 一句话定位

把散落在 QQ 群、学习通、雨课堂和口头通知里的**作业 / 表格 / 任务 / 考试**，收敛成一个按身份过滤、带倒计时和提醒的班级入口。

---

## 1. 背景与目标

### 1.1 三个真实痛点

| 角色 | 痛点 | 后果 |
|---|---|---|
| 普通同学 | 作业通知淹没在群聊里；表格接龙看不见；考试时间靠口口相传 | 漏交、漏填、迟到 |
| 班长 / 团支书 | 学院在班委群里派活，@ 一下就是任务，没人整理 | 漏办、被点名 |
| 全班 | 同一件事在 3 个平台各发一遍，信息互相矛盾 | 以谁为准说不清 |

### 1.2 产品目标

1. **一个入口**：所有"有截止时间的事"都能在一个列表 + 一个日历里看到。
2. **按身份过滤**：同学只看该看的，班委多一层"学院派给班委的活"。
3. **三种录入方式**：手动、群消息 AI 抽取、平台导入，最终都汇入同一张表。
4. **不漏事**：截止前自动提醒，过期单独归档。

### 1.3 非目标（本版明确不做）

- 不做作业提交、不做成绩管理（只做"什么时候截止"）。
- 不做即时聊天，不替代 QQ 群。
- 不做跨校 SaaS、不做多租户计费。
- 不承诺 100% 自动化抓取学习通/雨课堂（原因见 5.4）。

## 2. 角色与权限设计 ★

### 2.1 角色

| 角色 | 代码 | 说明 |
|---|---|---|
| 普通同学 | `student` | 班级成员，只读 + 标记本人完成 |
| 班长 | `monitor` | 班委，可读写本班全部条目 |
| 团支书 | `secretary` | 同班长（需求中两者权限一致，保留独立角色码便于日后细分） |
| 管理员 | `admin` | 部署者/班主任，管账号、数据源、机器人、LLM 配置 |

> 班委 = `monitor ∪ secretary`。所有"班委可见"的判断都走这个集合，不写死成某一个角色。

### 2.2 核心抽象：可见性只取决于"条目密级"，不取决于"类别"

这是整个权限设计的支点，先说结论：

> **`category`（作业/表格/任务/考试）只影响展示和统计；`audience`（密级）才决定谁能看见。**

```
audience = class       → 全班可见（作业、全班表格、全班任务、考试）
audience = committee   → 仅班委可见（学院下发给班委的任务、内部通知）
```

权限判定（后端唯一真源 `domain/policy.py`）：

```python
def can_view(user, item) -> bool:
    if item.class_id != user.class_id:      return False   # 数据隔离优先
    if item.status != "published":          return can_write(user, item)  # 草稿只有班委可见
    if item.audience == "class":            return True
    if item.audience == "committee":        return user.role in {"monitor", "secretary", "admin"}
    return False
```

**为什么不按类别做权限？** 因为一旦写成"作业→同学可见、学院任务→班委可见"，就会遇到"学院要求全班填的表"这种跨类情形：它既是"表格"（同学该看）又来自"学院"（班委才该看）。用 `audience` 一个维度就解开了——**来源决定密级，密级决定可见性，类别只是标签**。

### 2.3 权限矩阵

| 操作 | 游客 | 普通同学 | 班委 | 管理员 |
|---|:--:|:--:|:--:|:--:|
| 查看 `class` 条目（作业/表格/任务/考试） | — | ✅ | ✅ | ✅ |
| 查看 `committee` 条目（学院派给班委的任务） | — | ❌ | ✅ | ✅ |
| 查看条目关联的群消息原文/附件 | — | 随条目密级 | ✅ | ✅ |
| 手动新增 / 编辑 / 删除条目 | ❌ | ❌ | ✅（限本班） | ✅ |
| 提交"线索上报"（进草稿，不算正式条目） | ❌ | ✅ | ✅ | ✅ |
| 审核 AI / 上报产生的草稿 | ❌ | ❌ | ✅ | ✅ |
| 修改条目的密级 `audience` | ❌ | ❌ | ✅ | ✅ |
| 标记"我已完成 / 我已填写" | ❌ | ✅ | ✅ | ✅ |
| 查看完成统计、导出未完成名单 | ❌ | ❌ | ✅ | ✅ |
| 配置数据源 / 机器人 / LLM Key | ❌ | ❌ | ❌ | ✅ |
| 用户审批、角色变更、班级设置 | ❌ | ❌ | ❌ | ✅ |
| 查看审计日志 | ❌ | ❌ | 仅本人操作 | ✅ |

### 2.4 四条硬规则

1. **AI 永远不能直接发布。** 抽取结果一律落 `status=draft`，班委确认后才 `published`。可配置开关，但默认关闭自动发布。
2. **密级默认取严。** AI 判断不确定时给 `committee`，班委确认"这个全班能看"后再放开，而不是反过来。宁可晚一天让同学看到，也不要让学院内部要求被误公开。
3. **前端不设防。** 页面上的按钮显隐只是体验，所有读写都在后端按 `policy.py` 复核；越权返回 403，不是"看不见"。
4. **越权与不存在的响应一致。** 访问别人班的条目返回 404 而非 403，避免探测。

### 2.5 "线索上报"：给同学一个不越权的参与方式

同学在群里看到一条通知、或发现班委漏了某科作业，可以点"上报线索"：提交一段原文 + 截图，落到草稿箱。班委一键转正。这样既解决了"班委不可能看完所有群"，又没有给同学开放写权限。

## 3. 领域模型

### 3.1 ER 概览

```
classes 1──n users
classes 1──n deadlines 1──n completions
classes 1──n sources  1──n raw_messages 1──1 extraction_jobs
deadlines 1──n deadline_revisions
users   1──n audit_logs / sessions / notifications
```

### 3.2 表设计（SQLite / 可平移到 Postgres）

**users** — 账号与身份
`id, student_no UNIQUE, name, class_id, role, status(pending|active|disabled), password_hash, created_at, last_login_at`

**classes** — 班级
`id, name, college, major, grade, invite_code UNIQUE, created_at`

**deadlines** — 核心表，草稿与正式条目共用（靠 `status` 区分）
| 字段 | 说明 |
|---|---|
| `id, class_id` | 主键、所属班级（一切查询强制带 class_id） |
| `title, summary` | 标题 ≤60 字；AI 生成的摘要 |
| `category` | `homework` / `form` / `task` / `exam` |
| `audience` | `class` / `committee` ← 权限字段 |
| `course` | 课程名，可空（作业类常用） |
| `due_at` | UTC 时间戳（展示时转 Asia/Shanghai） |
| `due_at_raw` | 原文写法，如"下周三前"，留作对照 |
| `all_day, location, link, attachments_json` | 全天事项、地点（考试）、链接、附件 |
| `source_type` | `manual` / `qq` / `chaoxing` / `yuketang` / `bookmarklet` / `import` |
| `source_ref` | 原始消息 ID 或页面 URL |
| `status` | `draft` / `published` / `archived` |
| `confidence, needs_review` | AI 置信度、是否强制人工校对 |
| `dedupe_key` | 去重指纹（见 5.5） |
| `created_by, reviewed_by, published_at, created_at, updated_at` | 审计 |

索引：`(class_id, status, due_at)`、`(class_id, dedupe_key)`、`(class_id, audience, due_at)`

**completions** — 完成/填写状态（只对 `form` / `task` 启用）
`deadline_id, user_id, state(done|pending|skip), note, updated_at`，主键 `(deadline_id, user_id)`
> 班委看到的"已填 32/45 · 未填名单"就来自这张表。**建议纳入首版**，它是"催表格"场景的关键。

**sources** — 数据源配置
`id, class_id, type, name, config_json(脱敏), enabled, last_ok_at, last_error, created_at`

**raw_messages** — 原始消息落地（永不删除，是溯源与重跑的底料）
`id, source_id, external_id UNIQUE(去重), sender_name, sender_id, chat_name, content, attachments_json, occurred_at, ingested_at, status(new|extracted|ignored|failed)`

**extraction_jobs** — 每次抽取的完整记录
`id, raw_message_id, provider, model, prompt_version, raw_output, parsed_json, confidence, status, error, created_at`
> 保留原始输出 + prompt 版本，出问题能复盘，也能拿班委的修改当评测样本。

**deadline_revisions / audit_logs / notifications / sessions**
分别是字段级修改历史、操作审计、提醒任务、会话（便于强制下线）。

### 3.3 状态机

```
                    ┌───────── 班委驳回 ─────────┐
                    ▼                            │
  [draft] ──审核通过──> [published] ──到期30天──> [archived]
     ▲                       │
     └──── 手动/采集新建 ─────┘
```

- 只有 `published` 会出现在同学列表和提醒任务里。
- `archived` 仍可被班委检索，同学端折叠到"历史"。

## 4. 模块划分与职责

### 4.1 分层

```
┌──────────────────────────────────────────────────────────┐
│ 接入层  HTTP 路由 / 会话 / CSRF / 限流 / 静态资源          │
├──────────────────────────────────────────────────────────┤
│ 领域层  policy(权限) · deadlines(条目) · dedupe · 时间解析 │
├──────────────────────────────────────────────────────────┤
│ 服务层  Ingest(采集) · AI(抽取) · Notify(提醒) · Admin     │
├──────────────────────────────────────────────────────────┤
│ 基础层  SQLite · 迁移 · 备份 · 日志 · 配置                 │
└──────────────────────────────────────────────────────────┘
      ▲                    ▲                     ▲
   浏览器              QQ 机器人网关         定时任务线程
```

**模块之间只通过显式接口调用，不跨层读表。** 这是为了后续能整体替换（比如把 SQLite 换成 Postgres、把原生前端换成 React）。

### 4.2 模块职责表

| 模块 | 职责 | 不负责 | 对外接口 |
|---|---|---|---|
| `auth` | 注册审批、登录、会话、密码哈希、CSRF | 业务权限判断 | `login/logout/current_user` |
| `policy` | **唯一的权限判定真源**：可见/可写/可审核 | 数据查询 | `can_view/can_write/can_review` |
| `deadlines` | 条目 CRUD、查询过滤、倒计时分组、日历 | 数据来源解析 | `list/create/update/publish/archive` |
| `ingest` | 把各来源统一成 `RawItem` → 生成草稿 | 渲染、通知 | `Adapter.fetch/normalize` |
| `ai` | prompt、结构化输出、规则兜底、时间归一化、密级建议 | 直接写库 | `extract(RawItem) -> Draft` |
| `notify` | 截止前 T-24h / T-3h 提醒、每日摘要 | 内容生成 | `schedule/flush` |
| `jobs` | 定时调度（提醒扫描、平台同步、备份） | 业务逻辑 | 单线程 tick |
| `admin` | 用户/班级/数据源/机器人/LLM 配置 | — | — |

## 5. 数据来源与采集链路 ★

### 5.1 来源总览

| 来源 | 自动化程度 | 稳定性 | 合规/风险 | 结论 |
|---|---|---|---|---|
| 手动录入 | 人工 | 100% | 无 | **MVP 必做**，兜底一切 |
| QQ 群 @机器人 | 全自动 | 取决于机器人方案 | 个人号有封号风险 | 核心卖点，需选型 |
| 粘贴群消息/通知文本 | 半自动 | 高 | 无 | 零风险的 AI 入口 |
| 浏览器书签抓取 | 半自动（一键） | 较高 | 用户本机操作，风险低 | **推荐**替代服务端爬虫 |
| 服务端 cookie 抓取 | 全自动 | 低（验证码/改版/风控） | 存同学凭据，敏感 | 可选，不承诺 |
| CSV / Excel 导入 | 人工 | 100% | 无 | 学期初批量导入课程用 |

### 5.2 链路 A：手动录入

班委填表 → 前端校验 → 后端 `create` → 默认 `draft` 还是直接 `published`？**班委手动录入直接 published**，少一步。字段：标题、类别、密级、截止时间（日期+时间选择器）、课程、地点、链接、备注。

### 5.3 链路 B：QQ 群 @ 机器人（核心）

```
 群成员 @机器人 "下周三前交实验报告，学习通提交"
        │
        ▼
 [QQ 机器人] ──OneBot v11 WS──▶ [bot 网关] ──HTTP──▶ POST /api/ingest/qq
                                                        │
                                     ┌──────────────────┴──────────────────┐
                                     │ 1. 落 raw_messages（幂等去重）        │
                                     │ 2. 组装上下文：被 @ 的消息 + 引用消息  │
                                     │    + 发送者 + 群名 + 发送时间 + 时区   │
                                     │ 3. 调 AI 抽取 → Draft                │
                                     │ 4. 规则兜底 / 时间合理性校验          │
                                     │ 5. 落 deadlines(status=draft)        │
                                     └──────────────────┬──────────────────┘
                                                        ▼
                                        班委端「待确认」角标 +1
                                                        │
                                        审核（改密级/改时间）→ 发布 → 进同学列表 + 排提醒
```

**关键细节**

- **触发条件**：消息包含 @机器人 且带正文。只有 @ 不带正文 → 回复"请把要记的事一起 @ 我"。
- **上下文**：QQ 的"回复引用"要一并取到，否则"就按上面说的，周五前"这类指代无法解析。
- **幂等**：`raw_messages.external_id` 唯一；同一条消息被重复 @ 不会重复建草稿。
- **图片**：v1 只存图不 OCR；截图里的截止时间需班委手填。OCR 列为 P2。
- **失败不丢信息**：AI 挂了一律落 `failed` + 保留原文，班委端显示"有 1 条消息未解析，点击手动录入"。
- **机器人方案**（需你选）：HTTP 回调（官方机器人）/ OneBot v11 长连接（NapCat、LLOneBot 等）/ 半自动粘贴。三者都实现同一个 `ingest/qq.py` 入口，差别只在网关。

### 5.4 链路 C：学习通 / 雨课堂

**现实评估**：两者都没有公开 API。学习通的作业/考试列表需要登录态 cookie，雨课堂需要 `sessionid`，都带风控和验证码，页面结构随版本变化。**服务端长期无人值守抓取，维护成本会超过这个项目本身的价值。** 所以设计成三档，按投入递增：

| 档位 | 做法 | 服务器是否存凭据 | 稳定性 | 建议 |
|---|---|---|---|---|
| C1 粘贴 | 用户从 App/网页复制作业或通知文字，粘贴到"导入"框，走同一条 AI 管线 | 否 | 高 | **首版必做** |
| C2 书签抓取 | 站内生成一次性 token → 用户拖一行 JS 到书签栏 → 在学习通/雨课堂**已登录页面**点击，脚本读 DOM 提取作业标题/课程/截止时间 → POST 回站内 | 否 | 中高 | **强烈推荐** |
| C3 服务端轮询 | 用户在设置里填 cookie（加密存），后台每 6h 拉一次 | 是 | 低 | 可选，明确告知可能失效 |

C2 是这套设计里最划算的一招：**在用户已登录的浏览器里执行提取，服务器既不碰密码也不碰验证码**，失效时用户重登一下再点一次即可。学习通、雨课堂各写一个 DOM 选择器脚本，坏了单独改脚本，不影响主站。

统一抽象，三档共用：

```python
class SourceAdapter(Protocol):
    type: str
    def fetch(self, source) -> list[RawItem]: ...       # C1/C2 里是用户提交，C3 里是轮询
    def normalize(self, raw: RawItem) -> DeadlineDraft: ...
```

### 5.5 规范化与去重

所有来源最终产出同一种结构：

```json
{
  "title": "第 5 章实验报告",
  "category": "homework",
  "audience": "class",
  "course": "操作系统",
  "due_at": "2026-11-11T15:59:00Z",
  "due_at_raw": "下周三前",
  "link": "https://...",
  "confidence": 0.86,
  "needs_review": false
}
```

**去重指纹**：`sha1(class_id + 归一化标题 + 截止时间精度到天)`。命中已存在的 `published` 条目 → 不新建，只在原条目下追加一条"来源记录"；命中 `draft` → 合并字段取信息更全的。跨来源（群里说一遍、学习通又发一遍）靠这个收敛。

## 6. AI 抽取设计

### 6.1 管线

```
RawItem(text, sender, chat, occurred_at)
   │
   ├─ 预处理：去 @ 前缀、去表情、抽链接、判断是否"像任务"
   ├─ 上下文注入：当前时间(Asia/Shanghai) + 消息时间 + 本周日期表
   ├─ LLM 结构化输出（JSON Schema 约束）
   ├─ 后处理：时间合理性校验 / 密级规则覆写 / 置信度折算
   └─ Draft
```

### 6.2 输出 Schema

```json
{
  "is_task": true,
  "title": "提交第5章实验报告",
  "category": "homework",
  "audience_guess": "class",
  "audience_reason": "课程作业，面向全班",
  "course": "操作系统",
  "due_at": "2026-11-11T23:59:00+08:00",
  "due_at_raw": "下周三前",
  "missing_fields": [],
  "confidence": 0.86
}
```

### 6.3 相对时间解析（最容易出错的地方）

- LLM 输入里必须带**消息发生的日期**和**本周一到周日的具体日期**，否则"下周三"会被算错。
- 输出必须是带时区的 ISO8601；只给日期则默认 `23:59:59 +08:00`。
- 服务端二次校验，命中任一条即 `needs_review=true` 且禁止自动发布：
  - `due_at < 消息时间 - 1 天`（明显过去时）
  - `due_at > 消息时间 + 400 天`
  - 原文含"今天/明天/下周"但模型输出与规则解析结果相差 > 2 天 → 提示人工确认
- 同时保留**纯规则解析器**（正则 + 中文数字 + 星期推算）作为兜底：LLM 不可用时也能抽出"11月10日 23:59"这类明确写法。

### 6.4 密级推断规则（先规则，后模型）

```
含「学院/教务/辅导员/团委/年级」且含「班委/班长/团支书/各班」 → committee
含「考试/考场/监考」                                        → class（考试时间全班必须可见）
含「全班/各位同学/大家/请所有人」+ 作业/表格               → class
课程名 + 作业/报告/实验                                     → class
其余不确定                                                  → committee + needs_review
```

### 6.5 置信度与人工确认

| 置信度 | 处理 |
|---|---|
| ≥ 0.85 且无缺失字段 | 进草稿但标"低风险"，班委一键批量发布 |
| 0.5 ~ 0.85 | 正常待确认，高亮缺的字段 |
| < 0.5 或解析失败 | 不进草稿，进"未解析"队列，保留原文，班委手动建 |

**永远不自动发布**，哪怕 0.99。需求里"自动提取并加入列表"理解为"自动进入待确认列表"，最终落库由班委点头——这一条需要你确认（见 Q6）。

### 6.6 反馈闭环

班委每次修改 AI 结果，把 `(原文, 模型输出, 人工修正)` 存进 `extraction_jobs`。积累 50 条后可以做一个小评测集，改 prompt 前后跑分对比。这是这个项目从"能用"到"好用"的地方。

## 8. 技术架构与选型

### 8.1 当前环境的硬约束与应对（已定）

实测结论：

| 通道 | 状态 | 含义 |
|---|---|---|
| 命令行外网（npm / npmmirror / 清华 PyPI / jsdelivr / unpkg） | **全部 000** | 跑不了 `npm install`、`pip install`，Next.js / FastAPI 装不上 |
| 工具层 `web_fetch` | **可用** | 能取回单个**文本**文件（JS 源码、API 文档），取不了二进制包 |

你选定的是 Next.js / FastAPI 现代栈，但这个环境装不上依赖。硬写出来的 Next.js 工程我无法安装、无法启动、无法验证，交付的只是一堆没跑过的代码——这比不用现代栈更糟。

**最终方案：结构现代化，依赖归零。**

- 前端：**Preact 10 + htm**，从 CDN 取源码**本地化到仓库**（`web/vendor/`），无构建步骤。组件写法与 React 几乎一致（`html\`<div>...</div>\`` 对应 JSX），状态用 hooks，路由用 hash router。日后换 Next.js，组件可机械平移。
- 后端：**Python 3.13 标准库**实现 REST，严格按 `02-数据模型与接口契约.md` 的契约。路由/中间件/服务的分层与 FastAPI 工程同构，换框架只改 `server.py` 与 handler 签名。
- 数据库：SQLite（WAL）。DDL 已按可迁移到 Postgres 的写法给出。

这样今天就能给你一个**能点、能登录、能越权测试**的东西，而不是一个跑不起来的 Next.js 脚手架。等你的机器能连外网，替换成本大约：后端 1 天（handler 换装饰器），前端 2~3 天（htm 换 JSX + 接 Tailwind）。

> 如果你更希望"先给 Next.js 源码、等有网再跑"，告诉我，我把前端改成标准 React 工程结构（仍不安装依赖），但今天就没有可演示的页面。

### 8.2 方案 A 的具体选型

| 关注点 | 选择 | 理由 |
|---|---|---|
| 运行时 | Python 3.13（已装） | 标准库够用：`http.server`、`sqlite3`、`urllib`、`hmac`、`hashlib.scrypt`、`zoneinfo` |
| Web 框架 | 自写极简路由（~200 行） | 依赖为零；路由表 + 中间件链，分层与 FastAPI 同构 |
| 前端 | **Preact 10 + htm**（本地 vendor） | 组件化 + hooks，无构建；写法贴近 React，便于日后平移 |
| 样式 | 手写 CSS + design tokens（CSS 变量） | 免 Tailwind 构建；移动端优先 |
| 数据库 | SQLite（WAL 模式） | 单班几十人，写入极低；备份=复制文件 |
| 密码 | `hashlib.scrypt` + 随机盐 | 标准库自带，强度足够 |
| 会话 | HMAC 签名 Cookie + `sessions` 表 | 可强制下线 |
| 定时任务 | 后台守护线程 + 60s tick | 提醒扫描、平台同步、每日备份 |
| AI | DeepSeek `chat/completions`，`response_format=json_object`（`urllib` 直连） | 便宜、中文强；provider 可切换 |
| 部署 | `python -m app` + 可选 Caddy/Nginx；Dockerfile 基于 `python:3.13-slim` | 无构建产物 |

### 8.3 演进路径（写进 README，避免以后返工）

```
现在：Python stdlib + 原生前端
  ↓ 领域层不动，替换 web 层
中期：FastAPI + Pydantic（同进程换成 ASGI）
  ↓ API 契约不变，替换视图层
后期：Next.js / React 前端 + Postgres
```

前提是从第一行代码起就守住：**`domain/` 不 import 任何 web 框架；`api/` 只做参数校验和调用；SQL 集中在 `db.py` 的仓储函数里。**

### 8.4 部署形态

```
              ┌──────────── 云服务器 (1C2G 够) ────────────┐
 同学/班委 ──▶ │ Caddy :443 ──▶ app :8000 (systemd/docker) │
              │                    │                       │
              │              SQLite + 每日备份              │
              └────────────────────┼───────────────────────┘
                                   │
                        NapCat/官方机器人（同机或同网）
```

- 单进程即可，不要上 gunicorn 多 worker（SQLite 写冲突）。
- 备份：每日 `sqlite3 .backup` 到 `data/backups/`，保留 14 天。

## 9. 非功能设计

### 9.1 安全与隐私

- 密码 `scrypt`；会话 Cookie `HttpOnly + SameSite=Lax + Secure(生产)`。
- 所有写操作校验 CSRF token；登录接口限流（同 IP 5 次/分钟）。
- QQ 号、cookie、API Key 一律脱敏展示，日志不落明文。
- 群消息原文含个人信息，仅班委可见，普通同学看不到原文（只看到整理后的条目）。
- 学生数据导出仅 admin，且记审计。

### 9.2 性能

单班 ≤ 100 人、条目 ≤ 2000 条。SQLite 完全够。列表查询目标 < 50ms；页面首屏 < 300KB。

### 9.3 可用性与降级

| 故障 | 降级 |
|---|---|
| LLM 不可用 | 规则解析器兜底；抽取队列排队重试 |
| 机器人掉线 | 班委端显红点；仍可粘贴消息导入 |
| 平台抓取失效 | 自动停用该源并通知 admin |
| 数据库损坏 | 从最近备份恢复（数据丢失 ≤ 1 天） |

### 9.4 审计

谁在什么时候改了哪条条目的哪个字段（`deadline_revisions` 存前后值）。学院任务类条目建议强制留痕。
